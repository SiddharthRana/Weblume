# Security self-review

A self-review of the code against the build prompt (`docs/BUILD_PROMPT.md` §5, §7, §9 and §11), done on 2026-10-30. It isn't a penetration test or an audit, and it doesn't make Weblume "secure" or "compliant". It lists the measures taken, how each is tested, and the known gaps. Get an independent review before handling significant revenue or data.

## Measures and how they're tested

| Area                    | Measure                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Tested by                                                                                                                                    |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **SSRF** (§5)           | Only one module fetches user-influenced URLs (`apps/api/src/scanner/http/guarded-client.ts`). It resolves DNS, validates **every** address against a public-unicast allow-list, and connects to the validated IP (DNS pinning). It also: rejects alternative IP notations, credentials, non-HTTP(S) schemes and non-standard ports; follows at most 5 redirects, re-validated per hop; caps time and body size; sends no cookies and forwards no user headers; and blocks our own hosts | ~90 tests (`test/scanner/guarded-client.test.ts`, `ip-policy.test.ts`) against a local server with redirects, oversized and slow-drip bodies |

| **Authorisation**       | Every report read/write checks the owner ID on the server (`findOwned`). Other people's scans return the same 404 as missing ones. RLS on every table is a second layer                                                                                                                                                                                                                                                                                                                 | Cross-user tests in scans, accounts, billing and reports e2e; `pnpm db:verify` (RLS)                                                         |

## Known gaps, most important first

1. **CSP allows inline scripts** (`'unsafe-inline'`), because Next.js injects inline bootstrap scripts.
   - The policy still limits script, frame and connection origins.
   - Hardening means nonce-based CSP via the Next.js proxy (middleware); every page then becomes dynamically rendered.
   - The CSP with **real Turnstile and Paddle keys hasn't been tested**: check on staging.
2. **The mobile session isn't in encrypted storage.** `supabase_flutter`'s default storage is app-private `SharedPreferences`, now excluded from backups. Moving it to Android Keystore-backed storage (`flutter_secure_storage`) would protect it on rooted or compromised devices.
3. **Rate-limit counters are in memory, per instance.** Running several API instances multiplies the effective limits. Use a shared store (e.g. Redis) before scaling out.
4. **Sign-up abuse** relies on Supabase Auth's own rate limits and email confirmation. Turn on Supabase Auth CAPTCHA (Turnstile is supported) before a public launch.
5. **The scanner as an amplifier.** Someone could use Weblume to send requests at a third-party site. This is limited by:
   - Per-scan caps: 1 page, at most 50 link checks, and robots.txt is respected for links.
   - Per-IP and per-user rate limits, plus plan quotas.
   - A clear bot User-Agent with a contact page.

   Monitor `weblume_scans_started_total`, and block abusive accounts.

6. **The Dodo Payments adapter isn't verified against Dodo's live API** (see `payments-setup.md`). Paddle, Play and Pub/Sub were only tested against fakes.
7. **No MFA** for user accounts. Supabase supports TOTP; it isn't wired into the UI.
8. **No third-party penetration test** and no lawyer's review yet of the privacy policy and terms.
9. **Supabase settings live in the dashboard**: password policy, redirect URLs, SMTP and leaked-password protection. They must be set by hand; see the README.

## Checklist for each release

- [ ] `pnpm audit --prod --audit-level high` is clean (CI).
- [ ] No new `NEXT_PUBLIC_` variable holds a secret.
- [ ] New endpoints: DTO validation, an owner check, an entitlement check where relevant, and a rate limit for expensive work.
- [ ] New outbound requests to user-influenced hosts go through the guarded client.
- [ ] New log lines or Sentry context contain no emails, tokens, URLs with query strings, or report contents.
- [ ] Migrations keep RLS enabled; `pnpm db:verify` passes.
